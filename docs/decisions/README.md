# 架构决策记录

架构决策记录（ADR）保存重要技术取舍的上下文、选择、替代方案和后果。架构文档说明
“当前如何工作”，ADR 说明“为什么选择这样工作”。已接受（`accepted`）的 ADR 是
决策约束的权威来源，源码与测试是当前实现事实的权威来源；architecture 和 guide 是
这些约束与事实的正式投影，必须保持同步。Task 与角色反馈提供来源和证据；外部 memory
只能辅助发现仓库来源，不能脱离仓库来源独立约束任务。

## 编号与状态

- 文件名：`NNNN-short-title.md`，编号连续递增。
- “提议（`proposed`）”：正在讨论，不能作为决策约束或已实现行为的依据。
- “已接受（`accepted`）”：当前团队批准的决策约束，应在架构文档、指南和实现中
  保持一致。
- “部分取代（`partially superseded`）”：新 ADR 只替换旧 ADR 明确列出的决策条目
  或适用场景；未列出的部分继续有效。旧 ADR 标记为“部分取代”并链接新 ADR，
  新 ADR 明确写出被替换范围，两份文档互相链接。
- “已取代（`superseded`）”：由新 ADR 完整替换；旧文档保留并双向链接。
- “已拒绝（`rejected`）”：保留讨论结果，避免重复提出相同方案。

ADR 正式状态仅限以上五类。Task 或闭环产物另使用以下处置标记，它们不能冒充 ADR 状态：

- `candidate`：来源、适用范围或批准情况仍待确认的线索，不能作为决策约束。
- `conflict`：尚未裁定的冲突或偏离，必须交由 approver 处理，不能擅自选择一方。
- `exception`：已经 approver 明确批准的受限例外，只在记录的范围、条件和期限内有效。

尚未批准的例外申请只能标记为 `candidate` 或 `conflict`；获得批准前不得标为
`exception`，也不得作为决策约束。

## ADR 模板

```markdown
# ADR NNNN：标题

- 状态：提议
- 日期：YYYY-MM-DD
- 决策者：项目维护者
- 适用条件：哪些任务、边界或前置条件必须采用本决策
- 排除条件：哪些场景不适用，或需要另行决策
- 来源 Task：`../tasks/YYYY-MM-DD-<task-id>/summary.md`

## 上下文

描述问题、约束和必须作出决策的原因。

## 决策

写出一个可验证的选择。

## 替代方案

列出认真考虑过的方案及未采用原因。

## 影响

分别列出正面、负面和后续约束。

## 角色反馈与批准边界

- 角色反馈：记录架构、实现、测试等角色提出的意见及其处理结果；反馈本身不等于
  已接受决策。
- 批准者：明确谁有权批准本 ADR。
- 批准范围：明确批准覆盖的决策条目、适用条件和版本/阶段边界。
- 待批准或未覆盖事项：明确留在 Task 或另行建 ADR 的内容。

## 关系

- 取代/部分取代：列出被替换的 ADR、具体条目或场景。
- 被取代/被部分取代：列出后续 ADR（没有则写“无”）。
- 当前事实：链接受本决策影响的 architecture 文档。
- 执行方法：链接受本决策约束的 guide。
- 来源与验证：链接来源 Task 及其验证证据。

## 检索提示

列出下一次任务可能使用的自然语言关键词、目录/模块路径、决策问题和排除条件。
检索命中后应回到“适用条件”“排除条件”和“关系”核对，不把角色反馈或提议状态
当作已接受决策。

## 关联

链接架构文档、代码入口、来源 Task 和取代关系；关系字段应与关联链接保持一致。
```

修改 ADR 前阅读[文档维护指南](../guides/maintaining-docs.md)。
